## 1. IaC とは

**IaC（Infrastructure as Code）は、インフラ（VPC、サーバー、ロードバランサーなど）の構成を、コードとして書いて管理すること。**

### 手作業との比較

| | コンソールで手作業（Phase 2〜4） | IaC（Phase 5） |
|---|---|---|
| 同じ構成をもう一度作る | 手順書を見ながら、何十回もクリックする | コマンド1つ |
| 間違い | 入れ忘れ・選び間違いが起きやすい | コードに書いたとおりに毎回同じものができる |
| 何を変えたか | 分からない（覚えておくしかない） | Git の履歴に残る。レビューもできる |
| 今の構成が正しいか | コンソールを1つずつ見て回る | コードと比べられる（差分が見える） |
| 消す | 依存の順番を考えて、1つずつ消す | コマンド1つ（依存の順番はツールが考える） |
| 学ぶとき | 1つずつ意味を確かめられる | 中で何が起きているか見えにくい |

このプロジェクトが「コンソールで手作業 → CDK でコード化」の順にしているのは、手作業で意味を理解してから、コードで繰り返せるようにするため。

### 宣言的と手続き的

| | 手続き的（シェルスクリプトなど） | 宣言的（CloudFormation、CDK） |
|---|---|---|
| 書くこと | **やること**（「VPC を作る」「サブネットを作る」…）の順番 | **あってほしい状態**（「VPC が1つ、サブネットが4つある」） |
| 2回目に実行すると | もう一度作ろうとして、失敗したり重複したりする | 「もうある」と判断して、何もしない |
| 変更 | 「何をどう変えるか」を自分で書く | あってほしい状態を書き換えると、ツールが差分を計算して変える |

同じものを何度実行しても、結果が同じになる性質を **冪等性**（べきとうせい）と言う。宣言的な IaC は冪等。Phase 4 のユーザーデータは手続き的なので、2回実行しても壊れないように `if ! id -u statuspage` のような工夫を自分で入れていた。

## 2. CloudFormation

**AWS の IaC のサービス。** テンプレート（JSON か YAML）に「あってほしいリソース」を書くと、AWS がそのとおりに作る。CDK も、裏では CloudFormation を使っている。

| 用語 | 意味 |
|---|---|
| テンプレート | リソースの定義を書いたファイル |
| スタック | 1つのテンプレートから作ったリソースのまとまり。作る・変える・消すは、スタック単位で行う |
| 変更セット | 今のスタックとテンプレートを比べて、「何を追加・変更・削除するか」をまとめたもの。実行前に確認できる |
| ロールバック | 作成や変更の途中で失敗したら、**元の状態に自動で戻す**。中途半端な状態で止まらない |
| 出力（Outputs） | スタックから外に見せたい値（ALB の DNS 名など） |
| エクスポート | ほかのスタックから参照できるようにした出力 |

### 変更の種類

テンプレートを変えたとき、リソースごとに次のどれかになる。

| 種類 | 内容 | 例 |
|---|---|---|
| 変更なし | — | |
| その場で更新 | リソースを残したまま、設定だけ変える | Auto Scaling グループの希望の台数を変える |
| **置き換え** | **新しいリソースを作り、古いものを消す**。ID や名前が変わる | RDS の識別子を変える、サブネットの CIDR を変える |

置き換えは、データを持つリソース（RDS など）では特に注意する。`cdk diff` で「replace」と出たら、本当に置き換えてよいか確かめる。

## 3. AWS CDK

**AWS CDK（Cloud Development Kit）は、プログラミング言語（TypeScript、Python など）で書いたコードから、CloudFormation のテンプレートを作るツール。**

```
TypeScript のコード → cdk synth → CloudFormation テンプレート → cdk deploy → AWS のリソース
```

### CloudFormation を直接書く場合との違い

| | CloudFormation のテンプレート | CDK |
|---|---|---|
| 書く量 | 多い（VPC だけで数百行） | 少ない（`new ec2.Vpc(...)` で、サブネット・ルートテーブル・IGW までまとめて作る） |
| くり返し・条件 | 苦手 | プログラミング言語の `for`・`if`・関数が使える |
| 型のチェック | なし（デプロイして初めて間違いに気づく） | エディタが間違いを教えてくれる（TypeScript） |
| よくある設定 | 自分で全部書く | 安全な既定値が入っている（例：IAM の権限を自動で最小限にする） |
| 中で何が起きているか | 見たまま | 隠れている（`cdk synth` でテンプレートを見て確かめる） |

### 部品（コンストラクト）

CDK では、リソースを **コンストラクト** という部品として組み立てる。

| 階層 | 内容 | 例 |
|---|---|---|
| App | 全体。1つ以上のスタックを持つ | `bin/statuspage.ts` |
| Stack | CloudFormation のスタック1つに対応 | ネットワーク、DB、アプリ |
| Construct | スタックの中の部品 | VPC、ALB、Auto Scaling グループ |

コンストラクトには3つのレベルがある。

| レベル | 内容 | 例 |
|---|---|---|
| L1 | CloudFormation のリソースそのもの。名前が `Cfn` で始まる。全部の設定を自分で書く | `CfnVPC`、`CfnSubnet` |
| L2 | よく使う形にまとめ、安全な既定値を入れたもの。**ふだんはこれを使う** | `Vpc`、`ApplicationLoadBalancer`、`AutoScalingGroup` |
| L3 | 複数のリソースを組み合わせた、よくある構成 | `ApplicationLoadBalancedFargateService`（Phase 7 で出てくる形） |

### L2 の便利さと注意点

| 便利なこと | 例 |
|---|---|
| 関連するリソースを自動で作る | `Vpc` は、サブネット・ルートテーブル・IGW・ルートをまとめて作る |
| つながりを短く書ける | `dbSecurityGroup.connections.allowFrom(webSecurityGroup, ec2.Port.tcp(5432))` で、Phase 3 の手順2と同じルールができる |
| 権限を最小限で付ける | `secret.grantRead(role)` で、そのシークレットだけを読む IAM ポリシーができる |

| 注意すること | 例 |
|---|---|
| 自動で決まる値がある | `Vpc` のサブネットの CIDR は、指定しなければ CDK が順番に割り当てる |
| 思わぬリソースが増えることがある | `Vpc` は既定で、デフォルトのセキュリティグループのルールを消すための仕組み（Lambda 関数）も作る |

→ `cdk synth` や `cdk diff` で、実際に何が作られるかを必ず確かめる。

### バージョン

| 部品 | 内容 |
|---|---|
| `aws-cdk-lib` | コードから使うライブラリ（コンストラクト） |
| `aws-cdk`（CDK CLI） | `cdk` コマンド。ライブラリとは別にバージョンが付く |
| Node.js | CDK を動かす実行環境。LTS（長期サポート版）を使う |

## 4. CDK のコマンドと流れ

| コマンド | 内容 | AWS に変更を加えるか |
|---|---|---|
| `cdk bootstrap` | CDK が使う準備用のリソースを作る（[§5](#5-ブートストラップ)）。アカウントとリージョンごとに1回 | 加える |
| `cdk ls` | App の中のスタックの一覧 | 加えない |
| `cdk synth` | コードから CloudFormation テンプレートを作り、表示する（`cdk.out/` にも保存） | 加えない |
| `cdk diff` | 今 AWS にあるスタックと、コードから作ったテンプレートの差分を表示する | 加えない |
| `cdk deploy` | 差分を AWS に反映する（スタックを作る・変える） | 加える |
| `cdk destroy` | スタックを消す（中のリソースも消える。[§8](#8-削除するときの扱い)） | 加える |

- `--profile study` で、使う認証情報（Phase 0 の `aws login` のプロファイル）を指定する
- `-c 名前=値` で、デプロイのときに値を渡せる（コンテキスト）。コードに書きたくない値（自分の IP アドレスなど）に使う
- `cdk deploy` は、IAM やセキュリティグループに関わる変更があると、内容を表示して「本当にいいか」を聞いてくる

ふだんの流れは、**コードを変える → `cdk diff` で差分を読む → `cdk deploy`**。`diff` を読まずに `deploy` しない。

## 5. ブートストラップ

`cdk deploy` の前に、アカウントとリージョンごとに1回、`cdk bootstrap` を実行する。CDK がデプロイに使う道具を、`CDKToolkit` というスタックとして作る。

| 作られるもの | 用途 |
|---|---|
| S3 バケット | 大きなテンプレートや、Lambda のコードなどのファイル（アセット）を置く |
| ECR リポジトリ | コンテナイメージのアセットを置く（Phase 7 以降） |
| IAM ロール（数個） | デプロイを実行するためのロール。CDK CLI はこれを借りて CloudFormation を動かす |
| SSM パラメータ | ブートストラップのバージョンを記録する |

- 料金は、S3 と ECR に置いた量の分だけ（ほぼ0）
- `cdk deploy` で「ブートストラップされていない」というエラーが出たら、このリージョンでまだ実行していない

## 6. スタックの分け方

1つの App を、**一緒に作って一緒に消すもの（ライフサイクルが同じもの）** ごとにスタックに分ける。

| スタック | 中身 | ライフサイクル |
|---|---|---|
| ネットワーク | VPC、サブネット、ルートテーブル、IGW、セキュリティグループ | ほぼ変わらない。無料なので、ずっと残す |
| DB | DB サブネットグループ、RDS | **データを持つ**。めったに消さない。消すときはスナップショットを残す |
| アプリ | IAM ロール、起動テンプレート、ALB、ターゲットグループ、Auto Scaling グループ | よく変わる。**毎日消して作り直してもよい**（ALB は停止できないため） |

分けておくと、`cdk destroy` でアプリのスタックだけを消しても、DB のデータは残る。

### スタックをまたいだ参照

アプリのスタックは、ネットワークのスタックの VPC やセキュリティグループを使う。CDK では、別のスタックのコンストラクトをそのまま渡せば、CloudFormation のエクスポートとインポートが自動で作られる。

| 気をつけること | 理由 |
|---|---|
| 参照されているスタックは、先には消せない | 使われているものを消すと、使っている側が壊れるため。消すときは、参照している側（アプリ）から消す |
| 参照している値を変えるのが難しい | 使われているエクスポートは変更できない。先に使う側を変えてから、提供する側を変える |

## 7. 論理 ID と物理名

| 名前 | 内容 | 例 |
|---|---|---|
| 論理 ID | テンプレートの中での名前。CDK がコンストラクトの階層から作る | `AlbXXXXXXXX` |
| 物理名 | AWS の中での実際の名前・ID | `statuspage-db`、`sg-xxxx` |

### 物理名を付けるか、付けないか

| | 付けない（CDK に任せる。おすすめ） | 付ける |
|---|---|---|
| 名前 | `StatuspageApp-AlbXXXX-XXXX` のように自動で付く | 自分で決めた名前（`statuspage-alb` など） |
| 置き換えが必要な変更 | 新しい名前で作ってから古いものを消せる | **同じ名前のものを2つ同時に作れない**ので、変更が失敗することがある |
| 同じ App を2回デプロイする（別の環境） | 名前がぶつからない | ぶつかる |
| 人が探すとき | 探しにくい | 探しやすい |

- 物理名は、**ほかの仕組みが名前で探すもの** にだけ付ける。このプロジェクトでは、ユーザーデータが名前で探す RDS（`statuspage-db`）と、シークレット（`statuspage/db-app`）
- 論理 ID を変えると、CloudFormation は「別のリソース」とみなし、置き換えになる。コンストラクトの名前（`new X(this, '名前', ...)` の2つ目の引数）は、むやみに変えない

## 8. 削除するときの扱い

`cdk destroy` やコードからの削除で、リソースをどう扱うかを **削除ポリシー（RemovalPolicy）** で決める。

| ポリシー | スタックを消したとき | 向いているもの |
|---|---|---|
| `DESTROY` | リソースも消す | 作り直せるもの（ALB、EC2、セキュリティグループ） |
| `RETAIN` | **リソースを残す**（スタックの管理から外れるだけ） | 消えると困るが、作り直しも考えるもの |
| `SNAPSHOT` | **スナップショットを取ってから消す** | DB（RDS） |

- CDK の既定は、多くのリソースが `DESTROY`。データを持つもの（RDS、S3 バケットなど）は、既定が `SNAPSHOT` や `RETAIN` のものがある
- `RETAIN` で残ったリソースは、次に同じ物理名で作ろうとするとぶつかる。手で消すか、取り込む（[付録 C](phase5-appendix.md#c-既存のリソースを取り込む)）
- RDS の削除保護（Phase 3）を有効にすると、`cdk destroy` でも消せなくなる。本番ではこれも組み合わせる

## 9. 既存のリソースを使う

CDK で全部を作り直すときでも、**手で作って残したいもの** や、**ほかで管理しているもの** を使いたいことがある。

| 方法 | 内容 | このプロジェクトでの使い方 |
|---|---|---|
| 参照する（`fromXxx`） | 既存のリソースを、名前や ARN で **参照だけ** する。CDK は作りも消しもしない | アプリ用のシークレット `statuspage/db-app`（`Secret.fromSecretNameV2`） |
| スナップショットから作る | 既存の DB のスナップショットから、新しい DB を作る | 手で作った RDS の最終スナップショットから、`statuspage-db` を作り直す（`DatabaseInstanceFromSnapshot`） |
| 取り込む（`cdk import`） | 既存のリソースを、スタックの管理下に入れる | 使わない（[付録 C](phase5-appendix.md#c-既存のリソースを取り込む)） |

### スナップショットから作る DB と、パスワード

| ユーザー | パスワード |
|---|---|
| アプリ用（`statuspage`） | スナップショットの中に残っている。シークレット `statuspage/db-app` の値と一致しているので、そのまま使える |
| マスター（`postgres`） | スナップショットの中のパスワードは、手で作ったときの RDS 管理のシークレットと一緒に消えている。CDK に新しく作らせ、新しいシークレットに保存する |

## 10. 公開リポジトリで IaC を扱う

IaC のコードは Git に入れるので、**コードに書いたものは公開される**。

| 書かないもの | 代わりにどうするか |
|---|---|
| AWS アカウントID | CDK の環境変数 `CDK_DEFAULT_ACCOUNT`（認証情報から自動で決まる）を使う |
| 自分の IP アドレス（ALB に入れる場所） | `cdk deploy -c allowedCidrs=...` のように、デプロイのときに渡す |
| パスワード | Secrets Manager に置き、名前だけをコードに書く |
| `cdk.context.json` | `.gitignore` で除外する（下の表） |

### cdk.context.json

CDK は、AWS に問い合わせた結果（そのリージョンの AZ の一覧など）を `cdk.context.json` に保存し、次から使い回す。

| | 内容 |
|---|---|
| 公式のおすすめ | Git に入れる（チーム全員が同じ結果を使えるように） |
| このプロジェクト | **入れない**。中に `account=xxxxxxxxxxxx` の形でアカウントID が入るため |

### cdk.out

`cdk synth` が作るテンプレートの置き場所。アカウントID などが入ることがあり、毎回作り直されるので、Git に入れない（`.gitignore` 済み）。

## 11. ドリフト

**IaC で作ったリソースを、コンソールなどで手で変えて、コードと実物がずれた状態** をドリフトと言う。

| | 内容 |
|---|---|
| `cdk diff` で見えるか | **見えない**。`cdk diff` が比べるのは「前回デプロイしたテンプレート」と「今のコード」で、実物は見ていない |
| 見つけ方 | CloudFormation の「ドリフトの検出」。スタックごとに、実物とテンプレートを比べる |
| 次に `cdk deploy` すると | その項目をテンプレートが変えるときは、テンプレートの値で上書きされる。変えないときは、ずれたまま残る |
| 防ぎ方 | IaC で作ったものは、手で変えない。変えたくなったら、コードを変えてデプロイする |

## 12. 費用

| リソース | 料金 |
|---|---|
| CloudFormation、CDK | 無料（AWS のリソースを管理する分には） |
| ブートストラップ（S3、ECR、IAM、SSM） | 置いたファイルの分だけ。ほぼ0 |
| CDK が作るリソース | 手で作ったときと同じ（[Phase 4 §9](phase4-study.md#9-費用)） |
| `Vpc` が作る Lambda 関数（デフォルトのセキュリティグループのルールを消す仕組み） | 作るときに1回動くだけ。ほぼ0 |

- IaC にすると、**使わないときは消し、使うときに作る** が簡単になる。アプリのスタックを毎日 `cdk destroy` すれば、ALB の料金がかからない
- 移行の間、手で作った VPC と CDK の VPC が並ぶが、VPC・サブネット・セキュリティグループは無料

## 13. ほかの Phase とのつながり

### Phase 4 から何が置き換わったか

| Phase 4（手作業） | Phase 5（CDK） |
|---|---|
| コンソールで VPC・サブネット・ルートテーブルを1つずつ作る | `Vpc` コンストラクト1つ |
| セキュリティグループのルールを1つずつ追加する | `connections.allowFrom(...)` |
| IAM のインラインポリシーの JSON を手で書く | `secret.grantRead(role)` など |
| 起動テンプレートにユーザーデータを貼り付ける | `user-data.sh` を CDK が読み込む |
| 「毎回の終わり」に ALB を手で削除し、次の日に手順5をやり直す | `cdk destroy` / `cdk deploy` でアプリのスタックごと |
| 設定が正しいかを CLI で1つずつ確かめる | `cdk diff` でコードとの差分を見る |

アプリのコードは変えていない。

### この構成の弱点と、解決する Phase

| 弱点 | 解決 | Phase |
|---|---|---|
| `cdk deploy` を手元の PC から手で実行している | GitHub Actions から自動でデプロイする（OIDC で、アクセスキーなしで AWS に入る） | 6 |
| アプリのコードを変えても、動いているインスタンスには反映されない | 自動デプロイで、新しいインスタンスに入れ替える | 6 |
| インスタンスの起動に毎回パッケージを入れている | コンテナイメージ（ECR）から起動する | 7 |
| worker を1台に固定するために専用のインスタンスを動かし続けている | EventBridge + Lambda | 8 |

## 14. 理解度チェック

答えは自分で考えてから開く。

<details>
<summary>Q1. IaC にすると、手作業と比べて何がうれしい？ 逆に、手作業のほうが向いているのはどんなとき？</summary>

同じ構成をコマンド1つで何度でも作れる、間違いが起きにくい、変更の履歴が Git に残る、コードと比べて差分が分かる、依存の順番をツールが考えて消してくれる、など。初めて使うサービスの意味を1つずつ確かめながら学ぶときは、手作業のほうが向いている。
</details>

<details>
<summary>Q2. 「宣言的」とはどういうこと？ 同じ cdk deploy を2回続けて実行すると、2回目は何が起きる？</summary>

やることの順番ではなく、あってほしい状態を書くこと。2回目は、AWS にある状態とコードが同じなので、何も変えない（冪等）。
</details>

<details>
<summary>Q3. CDK と CloudFormation の関係は？ cdk synth は何をする？</summary>

CDK はプログラミング言語のコードから CloudFormation のテンプレートを作るツールで、実際にリソースを作るのは CloudFormation。`cdk synth` は、コードからテンプレートを作って表示する（AWS には何も変更しない）。
</details>

<details>
<summary>Q4. L1・L2・L3 のコンストラクトの違いは？ L2 を使うときに気をつけることは？</summary>

L1 は CloudFormation のリソースそのもの（`Cfn` で始まる）、L2 はよく使う形にまとめて安全な既定値を入れたもの、L3 は複数のリソースを組み合わせた構成。L2 は自動で決まる値や、自動で作られるリソースがあるので、`cdk synth` や `cdk diff` で実際に何が作られるかを確かめる。
</details>

<details>
<summary>Q5. cdk bootstrap は何のために、いつ実行する？</summary>

CDK がデプロイに使う道具（アセットを置く S3 バケット、デプロイ用の IAM ロールなど）を作るため。アカウントとリージョンごとに1回、最初の `cdk deploy` の前に実行する。
</details>

<details>
<summary>Q6. ネットワーク・DB・アプリの3つにスタックを分けたのはなぜ？ 消すときは、どの順番で消す？</summary>

ライフサイクルが違うから。アプリのスタックは ALB の料金のために毎日消して作り直したいが、DB はデータを持つので残したい。消すときは、ほかを参照している側から消す（アプリ → DB → ネットワーク）。
</details>

<details>
<summary>Q7. リソースに物理名を付けないほうがよいのはなぜ？ このプロジェクトで物理名を付けているのはどれで、なぜ？</summary>

置き換えが必要な変更のときに、同じ名前のものを2つ同時に作れず失敗することがあるから。また、同じ App を別の環境にデプロイすると名前がぶつかる。RDS（`statuspage-db`）とシークレット（`statuspage/db-app`）は、ユーザーデータが名前で探すので物理名を付けている。
</details>

<details>
<summary>Q8. RDS の削除ポリシーを SNAPSHOT にするのはなぜ？ DESTROY だと何が起きる？</summary>

スタックを消したときに、DB を消す前にスナップショットを取って、データを残すため。DESTROY だと、スタックを消すとデータごと消えて戻せない。
</details>

<details>
<summary>Q9. コンソールで、CDK が作ったセキュリティグループのルールを手で足した。cdk diff はそれに気づく？ どうすれば見つけられる？</summary>

気づかない。`cdk diff` は前回デプロイしたテンプレートとコードを比べるだけで、実物を見ていない。CloudFormation のドリフトの検出で見つけられる。IaC で作ったものは手で変えないのが原則。
</details>

<details>
<summary>Q10. 自分の IP アドレスや AWS アカウントID を、CDK のコードに書かないのはなぜ？ 代わりにどうする？</summary>

公開リポジトリに入るから。IP アドレスはデプロイのときにコンテキスト（`-c`）で渡し、アカウントID は認証情報から自動で決まる `CDK_DEFAULT_ACCOUNT` を使う。アカウントID が入る `cdk.context.json` と `cdk.out` も Git に入れない。
</details>

<details>
<summary>Q11. 手で作った RDS のデータを、CDK の RDS に引き継ぐにはどうした？ アプリ用のユーザーのパスワードはどうなる？</summary>

手で作った RDS を削除するときに最終スナップショットを作り、CDK でそのスナップショットから新しい RDS を作った。アプリ用のユーザー `statuspage` とそのパスワードはスナップショットの中に残っているので、手で作ったシークレット `statuspage/db-app` を参照してそのまま使える。
</details>

<details>
<summary>Q12. 「cdk deploy の差分に replace と出た」とき、何に気をつける？</summary>

置き換えは、新しいリソースを作って古いものを消すこと。ID や名前が変わり、データを持つリソースならデータが消えることもある。本当に置き換えてよいか、データの扱い（スナップショット、削除ポリシー）を確かめてからデプロイする。
</details>
