# docs の書き方

このフォルダの文書の種類と、書き方のルール。人が書くときも、AI（Claude など）に書かせるときも、このルールに従う。

## 文書の種類

| ファイル | 役割 | 書くもの | 書かないもの | GitHub |
|---|---|---|---|---|
| `phaseN-setup.md` | 手順書 | 何をするか（手順・コマンド）と、それに関する大まかな知識 | 確認結果、実測値、ログ、日付 | 上げる |
| `phaseN-study.md` | 知識まとめ | その Phase で使う知識を体系的に。どの環境でも通用する一般的な説明 | 今回の実行で起きたこと、時刻・計測値・容量、「実験Bでは〜」という語り | 上げる |
| `phaseN-appendix.md` | 付録 | その Phase では使っていないが、知っておくとよいもの（ない Phase もある） | 確認結果 | 上げる |
| `log/phaseN-result.md` | 確認結果 | 各手順で確認したこと、実測値、ログの抜粋、予想と結果、考えたこと | — | **上げない** |
| `log/`（その他） | 学習ログ | 自由に | — | **上げない** |

- 手順書・知識まとめ・付録は「誰が読んでも同じように使える」もの。自分の環境の結果は `log/` に分ける
- `log/` は `.gitignore` で除外されている。PC 間では共有されないので、必要なら手でコピーする

## 手順書（phaseN-setup.md）の形式

[phase0-setup.md](phase0-setup.md) を見本にする。

```markdown
# Phase N 手順書: タイトル

> 1〜2行の概要。
> 仕組みの解説は [phaseN-study.md](phaseN-study.md)、…は [phaseN-appendix.md](phaseN-appendix.md)。

## ゴール
- この Phase が終わったらできるようになること

## 環境
| 項目 | 値 |

---

## 0. 最初の手順

> 📖 **先に読む**
> - [study §X 見出し](phaseN-study.md#アンカー)：「小見出し」「小見出し」
>
> 読んだら考える：その手順の意味が分かったか確かめる問い

1. 手順
2. 手順

- 手順に関する大まかな知識（コマンドのオプションの意味、注意点など）

- [ ] 完了
```

- 手順は番号つきの見出し（`## 0.`、`## 1.` …）
- 各手順（小手順 `### 1-1.` があればその単位）の最初に **「📖 先に読む」** を置く。知識まとめの章へのリンクと、読むべき小見出しを「」で具体的に挙げ、「読んだら考える」の問いを1つ添える
- 実験の手順では、先に読むと答えが分かってしまうので **「📖 実験のあとに読む」** にする（問いは付けない）
- 最後にチェックボックス。チェックに結果や日付は書き足さない
- 実験では答えを書かない。「予想してから実行する」と「考えること」（観察するポイント・問い）だけを書く
- Windows（PowerShell）と macOS でコマンドが違うときは両方書く
- コードがリポジトリに用意済みの Phase では、「書く」ではなく「読む・動かす・実験する」手順にする

## 知識まとめ（phaseN-study.md）の形式

[phase0-study.md](phase0-study.md) を見本にする。

```markdown
# Phase N 知識まとめ: タイトル

> Phase N で出てきた知識を体系的にまとめたもの。手順は [phaseN-setup.md](phaseN-setup.md)。

## 目次
1. [見出し](#アンカー)
…
N. [理解度チェック](#…)

---

## 1. 見出し
（表・図・箇条書きで体系的に）

---

## N. 理解度チェック

答えは自分で考えてから開く。

<details>
<summary>Q1. 問い</summary>

答え
</details>

---

## 参考
- [公式ドキュメントへのリンク](https://...)
```

- 章は番号つき。最後の章は「理解度チェック」、その後に「参考」
- 理解度チェックの答えは必ず `<details>` で折りたたむ（`</summary>` の後に空行を入れる）
- 「AWS とのつながり」など、後の Phase との関係が分かる表を入れる

## 付録（phaseN-appendix.md）の形式

[phase0-appendix.md](phase0-appendix.md) を見本にする。冒頭で「この付録では次の◯つをまとめる」と A, B, C… の一覧を示し、各項目を `## A. 見出し` で書く。最後に「参考」。

## 確認結果（log/phaseN-result.md）の形式

```markdown
# Phase N 確認結果

> [phaseN-setup.md](../phaseN-setup.md) の各手順で確認したこと・実測値の記録。Git 管理外（GitHub には上げない）。

## 番号. 手順書と同じ見出し

- 予想 → 結果
- 実測値、ログの抜粋（日付と環境を添える）
- 疑問と答え、考えたこと
```

## 表記のルール

- **図より表を優先する**。枠線（`┌ │ └`）を使った図に日本語を入れない（全角文字の幅で枠がずれる）
  - 図を使うときは、枠の中を英数字だけにする。日本語の説明は行末の `←` の後に書く
  - ツリー（`├─ └─`）は、行末に日本語を置く形なら使ってよい
- 用語は初出で簡単に説明する（例：「接続プール（DB への接続を使い回す仕組み）」）
- 見出しのアンカーは GitHub の規則（記号や全角括弧は消え、空白は `-`）で書く。例：`## 6. データの置き場所（A と B）` → `#6-データの置き場所a-と-b`

## 書いてはいけないもの（公開リポジトリのため）

- AWS アカウントID、メールアドレス、アクセスポータルの URL
- アクセスキー、パスワード、`.pem` などの鍵
- IP アドレスやリソースID（`i-0abc...` など）。例として書くときは伏せ字にする（`i-xxxx`、`xxxxxxxxxxxx`）
