## 1. 冗長化とスケーリング

### 単一障害点

**そこが止まると、システム全体が止まってしまう部品** を単一障害点（SPOF：Single Point of Failure）と言う。

| 構成 | 単一障害点 |
|---|---|
| Phase 3 | EC2 1台（止まるとサイトが見られない）、AZ `2a`（EC2 も RDS も 2a にある）、RDS（Single-AZ） |
| Phase 4 | RDS（Single-AZ のまま）。EC2 は2つの AZ に複数台になる |

**冗長化** は、同じ役割の部品を複数用意して、1つが止まっても残りで動き続けられるようにすること。

### スケールアップとスケールアウト

| | スケールアップ（垂直） | スケールアウト（水平） |
|---|---|---|
| やり方 | 1台を大きくする（`t4g.micro` → `t4g.large`） | 台数を増やす（1台 → 3台） |
| 上限 | 一番大きいインスタンスまで | ほぼない |
| 止まるか | 大きさを変えるときに停止が必要 | 止めずに足せる |
| 冗長化になるか | ならない（1台のまま） | **なる** |
| 向いているもの | DB など、状態を持つもの | Web サーバーなど、状態を持たないもの（ステートレス） |

Phase 1 からアプリをステートレスに作ってきたのは、スケールアウトできるようにするため。

### マルチAZ

AZ（アベイラビリティゾーン）は、電源・ネットワーク・建物が独立したデータセンター群。**AZ が丸ごと止まる** ことも想定して、2つ以上の AZ にサーバーを分けて置く。

- Phase 4 では、api の EC2 を `2a` と `2b` に1台ずつ置く。片方の AZ が止まっても、もう片方で動き続ける
- DB は Single-AZ のまま。DB もマルチAZ にするには RDS の Multi-AZ（[phase3-appendix A](phase3-appendix.md#a-multi-az-配置とリードレプリカ)）が必要で、料金は約2倍

## 2. ロードバランサーと ALB

**ロードバランサーは、届いたリクエストを、後ろにある複数のサーバーに振り分ける受付係。** AWS の Elastic Load Balancing（ELB）には数種類あり、Web アプリには **ALB（Application Load Balancer）** を使う。

### 部品

```
client ──▶ ALB ── listener (HTTP :80) ── rule (default: forward) ──▶ target group ──▶ targets (EC2 ×2)
                                                                        └─ health check (/healthz)
```

| 部品 | 役割 |
|---|---|
| ロードバランサー | 入口。DNS 名を持つ |
| リスナー | 「どのポート・プロトコルで受け付けるか」（HTTP 80、HTTPS 443） |
| ルール | 受け付けたリクエストを、どこへ送るか。パスやホスト名で振り分け先を変えられる（例：`/api/*` は別のグループへ） |
| ターゲットグループ | 振り分け先のサーバーのまとまり。ヘルスチェックの設定もここに持つ |
| ターゲット | 振り分け先の1つ1つ（EC2 インスタンス、IP アドレス、Lambda など） |

ALB とターゲットグループは別の部品なので、ALB を作り直しても、ターゲットグループと、そこに登録しているもの（Auto Scaling グループ）は変えずに済む。

### L7（アプリケーション層）のロードバランサー

ALB は HTTP の中身（パス、ホスト名、ヘッダー）を読んで振り分ける。HTTPS の暗号化を ALB で受け持つこともできる（[§10](#10-https-と独自ドメイン)）。
TCP の通信をそのまま流すだけの NLB（Network Load Balancer）もある（[appendix F](phase4-appendix.md#f-alb-以外のロードバランサー)）。

### 振り分け方

- 既定は **ラウンドロビン**（順番に振り分ける）。ただし、ALB 自身が複数のノードで動いていて、ノードごとに順番を数えるので、きれいに交互になるとは限らない
- **Healthy なターゲットにだけ** 振り分ける（[§3](#3-ヘルスチェック)）
- 「最小未処理リクエスト」など、別の振り分け方も選べる

### ALB 自身も複数の AZ に置かれる

- ALB を作るときは、**2つ以上の AZ のサブネット** を指定する必要がある。ALB は、指定した各 AZ にノード（実体）を置く
- 1つの AZ が止まっても、もう1つの AZ のノードが受け付け続ける。ALB そのものが単一障害点にならない
- インターネット向けの ALB のノードは、パブリックサブネットに置く。ノードごとにパブリック IP アドレスを持つ

### DNS 名でアクセスする理由

ALB のノードの IP アドレスは、AWS が負荷に応じて増減させたり入れ替えたりするので **変わる**。そのため、ALB には IP アドレスではなく **DNS 名**（`xxxx.ap-southeast-2.elb.amazonaws.com`）でアクセスする。RDS のエンドポイント（Phase 3）と同じ考え方。

## 3. ヘルスチェック

ALB は、ターゲットグループの設定に従って、各ターゲットに定期的にリクエストを送り、**応答できるか** を確かめる。

### 設定値

| 設定 | 意味 | このプロジェクト |
|---|---|---|
| パス | どこにリクエストを送るか | `/healthz` |
| 間隔 | 何秒ごとに送るか | 10 秒 |
| タイムアウト | 何秒で返事がなければ失敗とするか | 5 秒 |
| 正常のしきい値 | 何回続けて成功したら Healthy にするか | 2 回 |
| 非正常のしきい値 | 何回続けて失敗したら Unhealthy にするか | 2 回 |
| 成功コード | どのステータスコードを成功とするか | 200 |

→ 壊れてから振り分けをやめるまで、最短で「間隔 × 非正常のしきい値」＝ 約20秒。間隔を短くすると早く気づけるが、チェックのリクエストが増える。

### ターゲットの状態

| 状態 | 意味 |
|---|---|
| Initial | 登録されたばかりで、チェック中 |
| Healthy | 正常。振り分ける |
| Unhealthy | 異常。振り分けない |
| Draining | 登録を外す途中（[§4](#4-登録解除の遅延)）。新しいリクエストは送らない |
| Unused | どの ALB からも使われていない、など |

### 何を確かめるべきか

- `/healthz` は、**そのサーバーのアプリが応答できるか** だけを返す（浅いヘルスチェック。[phase1-study §7](phase1-study.md#7-db-との接続と障害への備え)）
- DB まで確かめると、DB が落ちたときに全サーバーが Unhealthy になる。サーバーを入れ替えても DB は直らない
- 全ターゲットが Unhealthy になったとき、ALB は **全ターゲットに振り分ける**（フェイルオープン）。「誰にも送らない」よりはましという考え方
- ヘルスチェックは nginx（80番）経由で行われるので、nginx が止まっても、api が止まっても失敗する

## 4. 登録解除の遅延

ターゲットをターゲットグループから外す（インスタンスを終了する、台数を減らす）とき、ALB はすぐには外さない。

| 順番 | 起きること |
|---|---|
| ① | ターゲットの状態が **Draining** になる。**新しいリクエストは送らない** |
| ② | 処理中のリクエストが終わるのを、**登録解除の遅延**（既定 300 秒）まで待つ |
| ③ | 終わったら（または時間が来たら）、ターゲットから外す |

コネクションドレイン（Connection Draining）とも言う。台数を減らしたり入れ替えたりするときに、**処理中のリクエストを途中で切らない** ための仕組み。
Auto Scaling がインスタンスを終了するときは、この Draining が終わってから終了する。そのあと、インスタンスの中のアプリには systemd から SIGTERM が届く（[phase1-study §8](phase1-study.md#8-シグナルとプロセスの終了)）。

このアプリのリクエストはすぐ終わるので、遅延を 30 秒に短くしている。

## 5. 起動テンプレートとユーザーデータ

### 起動テンプレート

**インスタンスを起動するときの設定（AMI、インスタンスタイプ、セキュリティグループ、IAM ロール、ユーザーデータなど）を保存したもの。** Phase 2 で、起動画面に毎回手で入れていた内容を、名前を付けて残しておく。

- **バージョン** を持つ。変更すると新しいバージョンができ、古いバージョンも残る
- Auto Scaling グループは、起動テンプレートの「Latest（最新）」や特定のバージョンを指定して使う
- 起動テンプレートを変えても、**すでに動いているインスタンスは変わらない**。新しく起動するインスタンスから反映される（全台を入れ替える方法は [appendix D](phase4-appendix.md#d-起動テンプレートを更新して入れ替える)）
- サブネットは起動テンプレートに含めず、Auto Scaling グループの側で決める（複数の AZ に分けて置くため）

### ユーザーデータ

**インスタンスの初回起動時に、root で1回だけ実行されるスクリプト。** cloud-init というソフトが実行する。

| | Phase 2（手作業） | Phase 4（ユーザーデータ） |
|---|---|---|
| パッケージ、ユーザー、uv | Session Manager で1行ずつ | `user-data.sh` が自動で |
| コードの取得 | `git clone` | 同じ（`main` ブランチの最新） |
| DB の接続先とパスワード | 人が調べて、設定ファイルに書き込む | 起動時に AWS の API で取り出して書き込む |
| systemd、nginx | 手でコピーして起動 | 自動で |
| かかる時間 | 30分〜 | 数分（人は何もしない） |

- 実行のログは、インスタンスの中の `/var/log/cloud-init-output.log`
- api 用と worker 用で、スクリプトは同じで、先頭の `ROLE` だけ違う

### 接続先とパスワードをどう渡すか

ユーザーデータには、RDS のエンドポイントもパスワードも **書かない**。起動時に、インスタンスの IAM ロールの権限で取り出す。

| 情報 | 取り出し方 | 必要な IAM の権限 |
|---|---|---|
| RDS のエンドポイント | `aws rds describe-db-instances` | `rds:DescribeDBInstances`（`statuspage-db` だけ） |
| アプリ用のパスワード | `aws secretsmanager get-secret-value` | `secretsmanager:GetSecretValue`（`statuspage/db-app` だけ） |

書かない理由：

- ユーザーデータは、**インスタンスの中から誰でも読める**（IMDS で取り出せる）。パスワードを書くと、サーバーに入れる人や、乗っ取ったプログラムに読まれる
- 起動テンプレートの画面でも見える
- このスクリプトは公開リポジトリにある。エンドポイントのような環境ごとの値を書かなければ、誰が使っても同じスクリプトで済む
- RDS を作り直してエンドポイントが変わっても、スクリプトを変えなくてよい

スクリプトの中でも、パスワードを扱う行は `set +x`（実行した行をログに出す機能を止める）で囲み、ログにパスワードが残らないようにしている。

### うまくいかないときの確認

| 症状 | 確認すること |
|---|---|
| ターゲットが Healthy にならない | api のインスタンスで `sudo tail -n 50 /var/log/cloud-init-output.log`。どの行で止まったか |
| `AccessDenied`（ログの中） | IAM ロールのポリシー（`rds:DescribeDBInstances`、`secretsmanager:GetSecretValue`） |
| `uv sync` や `git clone` で失敗 | インスタンスがインターネットに出られるか（パブリック IP の自動割り当て、ルートテーブル） |
| DB につながらない | `statuspage-db-sg` に、そのインスタンスのセキュリティグループからのルールがあるか。RDS が停止していないか |
| インスタンスが起動しては終了されるのを繰り返す | ヘルスチェックの猶予期間が短すぎて、セットアップが終わる前に Unhealthy と判断されていないか |

## 6. Auto Scaling

**決めた台数のインスタンスを、起動テンプレートから自動で作り、保ち続けるサービス。** 正式には Amazon EC2 Auto Scaling。

### 部品

| 部品 | 役割 |
|---|---|
| Auto Scaling グループ | 台数を保つ単位。起動テンプレート、サブネット（AZ）、台数、ヘルスチェックの設定を持つ |
| 起動テンプレート | どんなインスタンスを作るか（[§5](#5-起動テンプレートとユーザーデータ)） |
| ターゲットグループ（任意） | 作ったインスタンスを、自動で登録・解除する先 |
| スケーリングポリシー（任意） | 台数を自動で変える条件（[appendix C](phase4-appendix.md#c-負荷に応じて自動で増減させる)） |

### 台数の3つの値

| 値 | 意味 |
|---|---|
| 希望するキャパシティ（desired） | 今、何台にしたいか |
| 最小（min） | これより減らさない |
| 最大（max） | これより増やさない |

- 希望は、最小と最大の間でなければならない。最大を超える値にはできない
- スケーリングポリシーは、最小と最大の範囲で「希望」を自動で変える

### 自己修復

Auto Scaling グループは、**実際の台数と、正常なインスタンスの数を、常に希望と比べている**。

| 起きたこと | Auto Scaling の動き |
|---|---|
| インスタンスが終了された（人が終了、ハードウェアの故障） | 足りない分を、起動テンプレートから新しく作る |
| インスタンスが Unhealthy と判断された | そのインスタンスを終了して、新しく作る |
| 希望を増やした | 新しく作る |
| 希望を減らした | 余分なインスタンスを終了する |

人が夜中に起きて直さなくても、決めた状態に戻る。そのためには、**どのインスタンスも使い捨てられる**（データを持たない、セットアップが自動）必要がある。

### ヘルスチェックの種類

| 種類 | 何を見るか | 見逃すもの |
|---|---|---|
| EC2（既定） | インスタンスが動いているか（EC2 のステータスチェック） | **OS は動いているが、アプリが応答しない** 状態 |
| ELB | ALB のヘルスチェックの結果 | — |

- ALB の後ろに置くグループでは、**ELB ヘルスチェックをオンにする**。オフのままだと、アプリが壊れたインスタンスは「ALB から振り分けられないだけ」で、いつまでも入れ替えられずに残る
- **猶予期間**（Health check grace period）：起動してからこの時間は、ヘルスチェックの失敗を数えない。ユーザーデータのセットアップが終わる前に「壊れている」と判断されないようにする

### AZ への配り方

- 複数の AZ のサブネットを指定すると、**AZ ごとの台数ができるだけ同じになるように** 配る
- 1つの AZ でインスタンスが作れないときは、ほかの AZ に作る。あとで、偏りを直す（リバランス）

### 減らすときに、どれを終了するか

既定のルール（終了ポリシー）では、おおむね次の順で決める。

1. インスタンスが一番多い AZ から選ぶ（AZ の偏りを減らす）
2. その中で、古い起動テンプレート（バージョン）で作られたものを選ぶ
3. その中で、次の課金の区切りに近いものを選ぶ

## 7. セキュリティグループのつながり

Phase 3 で学んだ「ソースにセキュリティグループを指定する」を、入口から DB までつなげる。

```
Internet ──80──▶ statuspage-alb-sg ──80──▶ statuspage-web-sg ──5432──▶ statuspage-db-sg
                  (from my IP)              (from alb-sg)               (from web-sg / worker-sg)
                                            statuspage-worker-sg ─5432──┘
                                            (no inbound)
```

| セキュリティグループ | 付ける先 | 受信を許可する相手 |
|---|---|---|
| `statuspage-alb-sg` | ALB | 自分の IP アドレス（HTTP 80） |
| `statuspage-web-sg` | api の EC2 | `statuspage-alb-sg`（HTTP 80） |
| `statuspage-worker-sg` | worker の EC2 | なし |
| `statuspage-db-sg` | RDS | `statuspage-web-sg` と `statuspage-worker-sg`（PostgreSQL 5432） |

- api の EC2 は、**ALB を通さずに直接アクセスされることがない**。ALB を通った通信だけが届く
- 外部からの許可を IP アドレスで書くのは、入口の ALB だけ。中の部品同士は、すべて役割（セキュリティグループ）で許可している
- api の EC2 が何台に増えても、作り直しても、ルールは変えなくてよい
- worker には受信ルールが1つもない。それでもインターネットへの通信（監視、パッケージ）はできる（ステートフル）

## 8. 複数台で動かすときの注意

1台のときは問題にならなかったことが、複数台にすると問題になる。

### 状態をサーバーに持たない

| サーバーに持つと困るもの | 理由 | このアプリでは |
|---|---|---|
| ログインの状態（セッション） | 次のリクエストが別のサーバーに行くと、ログインしていないことになる | ログインの機能がない |
| アップロードされたファイル | 別のサーバーからは見えない | ない |
| DB | サーバーを終了すると消える | RDS に分けた（Phase 3） |

### 1台だけで動かしたい処理

worker は「60秒ごとに全サイトを調べて記録する」処理。api と同じように2台にすると、**2台がそれぞれ同じサイトを調べ、記録が二重になる**。

| 方法 | 内容 | このプロジェクト |
|---|---|---|
| worker を api と別のグループにし、1台に固定する | 希望・最小・最大を 1 にした Auto Scaling グループ | **採用** |
| 何台動いても、1台だけが仕事をする | DB のロックなどで「リーダー」を1台決める（リーダー選出） | 使わない |
| 何回実行されても結果が変わらないようにする | 同じ時刻の記録を重複させない（冪等性） | 使わない |
| 定期実行をサービスに任せる | EventBridge が決まった時刻に1回だけ起動する | Phase 8 |

### 台数1の Auto Scaling グループ

- 台数を増やすためではなく、**壊れたら自動で作り直す（自己修復）ため** に使う
- 入れ替わりの間（数分）は監視が止まり、その間の記録はない
- 入れ替え方によっては、一時的に2台が同時に動くことがある（[appendix D](phase4-appendix.md#d-起動テンプレートを更新して入れ替える)）。その間だけ記録が二重になりうる

## 9. 費用

### このPhaseでかかるもの

| リソース | 課金の単位 | 止められるか |
|---|---|---|
| ALB | 時間 + LCU（処理量の単位） | **止められない**（削除するしかない） |
| ALB のパブリック IPv4 アドレス | AZ ごとに1つ × 時間 | ALB を削除すると消える |
| EC2（Auto Scaling が作ったもの） | 時間 | 希望を 0 にすると終了される |
| EC2 のパブリック IPv4、EBS | 時間 | インスタンスと一緒に消える |
| RDS | 時間 + ストレージ | 停止できる（最長7日） |
| ターゲットグループ、起動テンプレート、Auto Scaling グループ | 無料 | — |

- LCU（Load Balancer Capacity Unit）は、新しい接続の数、同時接続数、データ量、ルールの評価回数のうち、一番多いもので決まる。学習の量なら、1時間に1 LCU にも届かない

### 止め方

| やりたいこと | 方法 | 理由 |
|---|---|---|
| EC2 を止める | Auto Scaling グループの **希望・最小を 0** にする | インスタンスを「停止」しても、Auto Scaling は「正常でない」と判断して、新しく作ってしまう |
| ALB の料金を止める | ALB を **削除** する | ALB には「停止」がない |
| RDS を止める | 一時的に停止 | Phase 3 と同じ |

インスタンスは使い捨て（ユーザーデータで自動で作られる）なので、終了してもまた作ればよい。

## 10. HTTPS と独自ドメイン

この Phase の本編では HTTP（暗号化なし）を使っている。HTTPS にするには、**独自ドメイン** と **証明書** が必要になる。

| 部品 | 役割 | 料金 |
|---|---|---|
| ドメイン（例：`example.com`） | サイトの名前。登録業者（レジストラ）から年単位で借りる | 年に数ドル〜（ドメインの種類による） |
| Route 53 のホストゾーン | ドメインの DNS を管理する（`status.example.com` → ALB） | 月 $0.50 |
| ACM の証明書 | 「このドメインの持ち主だ」と証明し、HTTPS の暗号化に使う | **無料**（ALB などで使う公開証明書） |
| ALB の HTTPS リスナー | 443番で受け付け、暗号化を解いて EC2 に渡す | ALB の料金に含まれる |

- ALB の DNS 名（`xxxx.elb.amazonaws.com`）のための証明書は作れない。HTTPS には自分のドメインが必要
- ACM は、ドメインの DNS に決められたレコードを置けるかどうかで、持ち主かを確かめる（DNS 検証）
- **AWS のクレジットは、Route 53 でのドメイン登録には使えない**。登録すると、クレジットカードに請求される
- 手順は [appendix A](phase4-appendix.md#a-独自ドメインと-https)

### TLS 終端

HTTPS の暗号化を、ALB で解くことを「ALB で TLS を終端する」と言う。

```
browser ──HTTPS(443)──▶ ALB ──HTTP(80)──▶ EC2
          encrypted            plain, inside the VPC
```

- 証明書の管理（更新）を ALB と ACM に任せられる。EC2 に証明書を置かなくてよい
- ALB から EC2 までは VPC の中の通信。さらに暗号化したい場合は、EC2 でも HTTPS にする
- アプリから見ると、すべて HTTP で届く。元が HTTPS だったかは、ALB が付ける `X-Forwarded-Proto` ヘッダーで分かる
- ALB とアプリの間にもう1段プロキシ（nginx）があるときは、そのプロキシが ALB のヘッダーを **そのまま** 渡す必要がある。nginx で `proxy_set_header X-Forwarded-Proto $scheme;` と書くと、`$scheme` は「nginx が受け取ったときのプロトコル」（ALB の後ろでは常に `http`）なので、ALB の値を上書きしてしまう。ALB の後ろでは `$http_x_forwarded_proto`（受け取ったヘッダーの値）を渡す

## 11. ほかの Phase とのつながり

### Phase 3 から何が置き換わったか

| Phase 3 | Phase 4 |
|---|---|
| EC2 1台を手で作り、手でセットアップ | 起動テンプレート + ユーザーデータで自動 |
| 入口は EC2 のパブリック IP（停止で変わる） | 入口は ALB の DNS 名（変わらない） |
| EC2 が止まるとサイトも止まる | 2つの AZ に2台。1台止まっても動き続け、自動で作り直される |
| `statuspage-web-sg` は自分の IP から 80番 | `statuspage-web-sg` は ALB からだけ。自分の IP は `statuspage-alb-sg` へ |
| api と worker は同じ EC2 | api と worker は別々のグループ |

### この構成の弱点と、解決する Phase

| 弱点 | 解決 | Phase |
|---|---|---|
| VPC、セキュリティグループ、ALB、Auto Scaling などを、コンソールで手で作った。もう一度作るのが大変で、間違えやすい | AWS CDK でコード化 | 5 |
| コードを更新しても、動いているインスタンスには反映されない（起動時の `git clone` だけ） | GitHub Actions で自動デプロイ | 6 |
| インスタンスの起動に数分かかる（毎回パッケージを入れ、`uv sync` する） | 準備済みのイメージ（コンテナ）から起動する | 7 |
| OS の更新など、EC2 の面倒を見る必要がある | ECS Fargate | 7 |
| worker を1台に固定するために、専用のインスタンスを動かし続けている | EventBridge + Lambda で、1分ごとに1回だけ実行する | 8 |
| RDS は Single-AZ。DB の AZ が止まると止まる | RDS の Multi-AZ（料金は約2倍） | （必要に応じて） |
| HTTP のまま | 独自ドメイン + ACM で HTTPS | [appendix A](phase4-appendix.md#a-独自ドメインと-https) |

## 12. 理解度チェック

答えは自分で考えてから開く。

<details>
<summary>Q1. スケールアップとスケールアウトの違いは？ 冗長化になるのはどちら？</summary>

スケールアップは1台を大きくすること、スケールアウトは台数を増やすこと。冗長化になるのはスケールアウト。スケールアップは1台のままなので、その1台が止まれば全体が止まる。
</details>

<details>
<summary>Q2. ALB を作るのに、2つ以上の AZ のサブネットが必要なのはなぜ？</summary>

ALB は指定した AZ ごとにノード（実体）を置くので、1つの AZ が止まっても、もう1つの AZ のノードが受け付け続けられる。ALB そのものを単一障害点にしないためで、AWS のルールとして2つ以上が必須になっている。
</details>

<details>
<summary>Q3. ALB のリスナー、ルール、ターゲットグループ、ターゲットは、それぞれ何？</summary>

リスナーは、どのポート・プロトコルで受け付けるか（HTTP 80 など）。ルールは、受け付けたリクエストをどこへ送るかの条件（パスやホスト名）。ターゲットグループは、振り分け先のまとまりで、ヘルスチェックの設定を持つ。ターゲットは、振り分け先の1つ1つ（EC2 インスタンスなど）。
</details>

<details>
<summary>Q4. ALB に IP アドレスではなく DNS 名でアクセスするのはなぜ？</summary>

ALB のノードの IP アドレスは、AWS が負荷に応じて増減・入れ替えをするので変わるから。DNS 名は変わらず、そのときのノードの IP アドレスを指す。
</details>

<details>
<summary>Q5. ヘルスチェックの間隔が 10 秒、非正常のしきい値が 2 回のとき、アプリが壊れてから振り分けが止まるまで、最短でどのくらい？ その間のリクエストはどうなる？</summary>

最短で約 20 秒（10 秒 × 2 回）。その間は、壊れたターゲットにも振り分けられるので、一部のリクエストがエラーになる。
</details>

<details>
<summary>Q6. 登録解除の遅延（コネクションドレイン）は、何のためにある？</summary>

ターゲットを外すときに、処理中のリクエストを途中で切らないため。外すと決めたターゲットには新しいリクエストを送らず（Draining）、処理中のものが終わるのを決めた時間まで待ってから外す。
</details>

<details>
<summary>Q7. Auto Scaling グループのヘルスチェックを「EC2」だけにしていると、nginx が止まったインスタンスはどうなる？</summary>

EC2 のヘルスチェックは、インスタンスが動いているかしか見ないので、正常と判断され続ける。ALB からは Unhealthy なので振り分けられないが、Auto Scaling は入れ替えないので、壊れたインスタンスがいつまでも残る。ELB ヘルスチェックをオンにすると、ALB の結果を使って入れ替えられる。
</details>

<details>
<summary>Q8. ヘルスチェックの猶予期間は、何のためにある？ 短すぎると何が起きる？</summary>

起動してからユーザーデータのセットアップが終わるまで、ヘルスチェックの失敗を数えないため。短すぎると、セットアップが終わる前に Unhealthy と判断されて終了され、新しいインスタンスがまた同じ目にあう、という繰り返しになる。
</details>

<details>
<summary>Q9. Auto Scaling で作るインスタンスを、コンソールで「停止」するとどうなる？ 料金を止めたいときはどうする？</summary>

Auto Scaling は、停止したインスタンスを正常でないと判断して終了し、新しいインスタンスを作る。料金を止めたいときは、Auto Scaling グループの希望・最小を 0 にする。
</details>

<details>
<summary>Q10. ユーザーデータに、DB のパスワードや RDS のエンドポイントを直接書かないのはなぜ？ 代わりにどうしている？</summary>

ユーザーデータは、インスタンスの中から誰でも読め（IMDS）、起動テンプレートの画面でも見えるので、パスワードを書くと漏れる。エンドポイントは環境ごとに違い、RDS を作り直すと変わるので、書くとスクリプトを直す必要がある。代わりに、起動時にインスタンスの IAM ロールの権限で、Secrets Manager からパスワードを、RDS の API からエンドポイントを取り出している。
</details>

<details>
<summary>Q11. api の EC2 のセキュリティグループで、80番のソースを自分の IP アドレスから statuspage-alb-sg に変えたのはなぜ？</summary>

外からの入口を ALB だけにするため。EC2 に直接アクセスできると、ALB のヘルスチェックや振り分けを通らないアクセスができてしまい、入口を ALB にまとめた意味がなくなる。また、EC2 が何台になっても、作り直しても、ルールを変えなくてよい。
</details>

<details>
<summary>Q12. worker を api と同じ Auto Scaling グループに入れて2台にすると、何が困る？ 台数1の Auto Scaling グループにするのは何のため？</summary>

2台がそれぞれ同じサイトを調べるので、監視の記録が二重になる。台数1の Auto Scaling グループにするのは、台数を増やすためではなく、worker が壊れたり終了されたりしたときに、自動で作り直す（自己修復）ため。
</details>

<details>
<summary>Q13. ALB の後ろの EC2 には HTTP で届くのに、利用者は HTTPS で使える構成を何と言う？ そのときアプリは、元が HTTPS だったことをどう知る？</summary>

ALB で TLS を終端する構成。ALB が暗号化を解いて、EC2 には HTTP で渡す。アプリは、ALB や nginx が付ける X-Forwarded-Proto ヘッダーで、元のプロトコルを知る。
</details>

<details>
<summary>Q14. 学習を中断している間も、この Phase でかかり続ける料金は何？ 止めるにはどうする？</summary>

ALB（時間の料金と、パブリック IPv4 アドレス2つ）、RDS のストレージ、シークレット。ALB は停止できないので、1日以上空けるなら削除する。EC2 は Auto Scaling グループの希望・最小を 0 にし、RDS は一時的に停止する。
</details>
