## 1. コンテナとオーケストレーション

### EC2 にアプリを載せるときの手間

Phase 2〜6 では、EC2 を起動するたびに、ユーザーデータが次のことをしていた。

| やること | 問題 |
|---|---|
| OS のパッケージ（git、nginx）を入れる | 起動のたびに同じことをするので遅い |
| uv を入れ、GitHub からコードを取り、PyPI からライブラリを入れる | 外のサービスが落ちていると起動できない。取るタイミングで中身がずれうる |
| systemd のサービスを登録して起動する | 手順が長く、どこで失敗したかを追いにくい |

### コンテナにすると

**コンテナイメージ**は、アプリと、動かすのに必要なもの（Python、ライブラリ、設定）を全部入れて固めたもの。Phase 1 の `docker compose` で使ったものと同じ。

| | EC2 + ユーザーデータ | コンテナ |
|---|---|---|
| 準備をするとき | 起動のたび、各マシンの中で | イメージを作るとき、1回だけ |
| 起動するときにすること | 準備をすべて | イメージを取ってきて、プロセスを起動するだけ |
| 入れ替えにかかる時間 | 数分 | 数十秒ほど |
| どの台も同じ中身か | タイミングによってずれうる | 同じイメージなら必ず同じ |
| 手元との違い | 手元は Docker、本番は systemd | 手元も本番も同じイメージ |

### オーケストレーション

コンテナを1つ動かすだけなら `docker run` でよい。本番では、次のことも必要になる。

- 決めた数を動かし続ける（落ちたら起動し直す）
- 複数のマシン・AZ に散らばらせる
- ロードバランサーに登録・解除する
- 新しいバージョンに少しずつ入れ替え、失敗したら戻す

これをまとめて行う仕組みを **オーケストレーション**（指揮）と呼ぶ。AWS では **ECS**（Elastic Container Service）と **EKS**（Kubernetes）がある。このプロジェクトでは、設定が少なく AWS の他のサービスとつなぎやすい ECS を使う（EKS との比較は [付録 E](phase7-appendix.md#e-ecs-以外の選択肢)）。

| Phase 4〜6 の役目 | Phase 7 で代わるもの |
|---|---|
| Auto Scaling グループ（台数を保つ、入れ替える） | ECS のサービス |
| 起動テンプレート（何を起動するか） | ECS のタスク定義 |
| ユーザーデータ（起動時の準備） | イメージ（準備は作るときに済ませる） |
| systemd（プロセスを動かし続ける） | ECS（コンテナが止まったら起動し直す） |
| nginx（ALB との間に立つ） | なし。ALB がコンテナに直接送る |

## 2. コンテナイメージと ECR

### レジストリ

イメージの置き場所を **レジストリ**、その中の1つのイメージの入れ物を **リポジトリ** と呼ぶ（Git のリポジトリとは別のもの）。

| レジストリ | 例 |
|---|---|
| Docker Hub | `python:3.13-slim` など、公式イメージの置き場所 |
| ECR Public | AWS が公開しているレジストリ。Docker Hub の公式イメージの写しもある（`public.ecr.aws/docker/library/python`） |
| **ECR**（Elastic Container Registry） | 自分のアカウントの、非公開のレジストリ。このプロジェクトのイメージを置く |

ECR のイメージの名前は `<アカウントID>.dkr.ecr.<リージョン>.amazonaws.com/<リポジトリ名>:<タグ>` の形になる。

### タグ

タグはイメージに付ける名札。

| 付け方 | よいところ | 気をつけること |
|---|---|---|
| `latest` | 簡単 | 中身がいつでも変わる。どのバージョンが動いているか分からない |
| `v1.2.0` | 人が読める | 付け忘れ・付け間違いがありうる |
| **コミット SHA**（このプロジェクト） | コードと1対1で対応する。Phase 6 の `appVersion` と同じ値 | 長い |

ECR の **タグのイミュータビリティ**（不変）を有効にすると、同じタグで別のイメージを上書きできなくなる。「この SHA のイメージ」の中身が、あとから変わらないことを保証できる。

### ECR の設定

| 設定 | 意味 |
|---|---|
| タグのイミュータビリティ | 同じタグの上書きを禁止する |
| プッシュ時にスキャン | 置いたときに、イメージの中のパッケージに知られた脆弱性がないかを調べる（基本スキャン、無料） |
| ライフサイクルポリシー | 古いイメージを自動で消す（「新しい10個だけ残す」など）。置いた量で課金されるため |

### プラットフォーム（CPU の種類）

イメージは、CPU の種類（**アーキテクチャ**）ごとに作られる。

| アーキテクチャ | 例 |
|---|---|
| `arm64` | Graviton（`t4g` の EC2、Fargate の ARM）、Apple シリコンの Mac |
| `amd64`（x86_64） | Intel・AMD の PC、多くの Windows PC |

ARM の Fargate で動かすには、`arm64` のイメージが必要。`docker build --platform linux/arm64` で指定する。PC と違う種類のイメージを作るときは、Docker がエミュレーション（別の CPU のふり）をするので遅くなる。

### ベースイメージの取得元

`FROM python:3.13-slim` は Docker Hub から取ってくる。Docker Hub は、ログインしない取得に回数の制限がある（IP アドレスごと）。CodeBuild のように多くの人と IP アドレスを共有するマシンでは、制限に当たって失敗することがある。同じ公式イメージを ECR Public（`public.ecr.aws/docker/library/python:3.13-slim`）から取ると、この問題を避けられる。

## 3. ECS の部品

| 部品 | 意味 | EC2 の構成でいうと |
|---|---|---|
| **クラスター** | タスクとサービスをまとめる入れ物。名前空間のようなもの | — |
| **タスク定義** | 「どのイメージを、どれだけの CPU・メモリで、どんな環境変数で動かすか」の設計図。変えるたびに新しい **リビジョン**（版）になる | 起動テンプレート |
| **タスク** | タスク定義から起動した、動いているコンテナ（のまとまり） | インスタンス |
| **サービス** | 「このタスク定義のタスクを、いつも N 個動かす」を守る仕組み。ロードバランサーへの登録や入れ替えもする | Auto Scaling グループ |
| コンテナ定義 | タスク定義の中の、1つのコンテナの設定（イメージ、ポート、環境変数、ログ、コマンド） | ユーザーデータの中身 |

### タスクとサービスの違い

| | 単独のタスク（「タスクを実行」） | サービス |
|---|---|---|
| 止まったら | そのまま。誰も起動し直さない | 決めた数に戻すため、新しいタスクを起動する |
| ロードバランサー | 登録されない | 登録・解除してくれる |
| 向いているもの | 1回で終わる処理（DB の移行など） | ずっと動かすもの（api、worker） |

### このプロジェクトのタスク定義

api と worker は、同じイメージを別のコマンドで動かす（Phase 1 の `compose.yaml` と同じ考え方）。

| | api | worker |
|---|---|---|
| コマンド | イメージの既定（`uvicorn ...`） | `python -m statuspage.worker` |
| ポート | 8000 | なし |
| 数 | 2 | 1（監視の二重実行を避ける） |
| ロードバランサー | ALB に登録する | 登録しない |

## 4. Fargate

ECS のタスクを動かす場所は2種類ある。

| | **Fargate**（このプロジェクト） | EC2 起動タイプ |
|---|---|---|
| マシン | AWS が用意する。見えない | 自分の EC2 を ECS に登録する |
| OS の更新・台数の管理 | いらない | 自分でする |
| 決めるもの | タスクごとの CPU とメモリ | EC2 の種類と台数、詰め込み方 |
| 料金 | タスクの CPU・メモリ × 動いた時間 | EC2 の料金 |
| 向いているもの | 小さく始める、管理を減らす | 大量に動かす、GPU など特別なマシンが要る |

EC2 起動タイプは [付録 A](phase7-appendix.md#a-ec2-起動タイプと容量プロバイダー)。

### CPU とメモリ

Fargate では、CPU（vCPU）とメモリの組み合わせを選ぶ。一番小さいのは 0.25 vCPU・0.5 GB。このアプリは軽いので、これで足りる。

| 指定 | 意味 |
|---|---|
| `cpu: 256` | 0.25 vCPU（1024 で 1 vCPU） |
| `memory: 512` | 512 MiB |
| `cpuArchitecture: ARM64` | Graviton で動かす。x86 より2割ほど安い |

## 5. タスクのネットワーク

### awsvpc モード

Fargate のタスクは、**タスクごとに ENI**（ネットワークの差し込み口）を1つもらい、自分のプライベート IP アドレスとセキュリティグループを持つ。EC2 のインスタンス1台と同じように扱える。

| | EC2 の構成 | Fargate |
|---|---|---|
| IP アドレスを持つもの | インスタンス | タスク |
| セキュリティグループを付けるもの | インスタンス | タスク |
| ALB のターゲットの種類 | インスタンス（`instance`） | **IP アドレス（`ip`）** |
| ALB が送る先のポート | 80（nginx） | 8000（コンテナ） |

### パブリック IP とイメージの取得

タスクは起動するとき、ECR からイメージを、Secrets Manager から秘密を取ってくる。どちらも AWS のサービスの入口（インターネット側）にある。

| 置き方 | 外に出る道 | 費用 |
|---|---|---|
| **パブリックサブネット + パブリック IP**（このプロジェクト） | インターネットゲートウェイ | パブリック IPv4 の料金だけ |
| プライベートサブネット + NAT ゲートウェイ | NAT ゲートウェイ | NAT ゲートウェイが高い（時間 + 通信量） |
| プライベートサブネット + VPC エンドポイント | AWS の中だけ | エンドポイントごとに時間の料金 |

パブリック IP を付けても、セキュリティグループで「ALB からの 8000 番だけ」を許可すれば、外から直接は入れない（Phase 4 の web の SG と同じ考え方）。パブリック IP を付け忘れると、外に出る道がないので、イメージを取れずに起動に失敗する。プライベートサブネットに置く方法は [付録 C](phase7-appendix.md#c-プライベートサブネットに置く)。

### セキュリティグループのつながり

| SG | 受け入れるもの |
|---|---|
| alb | 自分の IP アドレスから 80 番 |
| web（api のタスク） | alb の SG から 8000 番 |
| worker（worker のタスク） | なし |
| db | web と worker の SG から 5432 番 |

## 6. タスクの2つのロールと秘密

ECS のタスクには、IAM ロールが2つある。名前が似ているので、使う人で区別する。

| ロール | 使う人 | 使う場面 | このプロジェクトでの許可 |
|---|---|---|---|
| **タスク実行ロール** | ECS（タスクを起動する側） | イメージを取る、ログの置き場所に書く、秘密を読んで環境変数に入れる | ECR からの取得、CloudWatch Logs への書き込み、`statuspage/db-app` の読み取り |
| **タスクロール** | アプリ（コンテナの中のコード） | アプリが AWS の API を呼ぶ（S3 に置く、など） | なし（アプリは AWS の API を呼ばない） |

EC2 では、インスタンスのロール1つに両方の役目を持たせていた。ECS では、起動の仕組みとアプリの権限が分かれるので、アプリに余計な権限を渡さずに済む。

### 秘密を環境変数に入れる

タスク定義の `secrets` に、Secrets Manager のシークレットの ARN を書くと、ECS がタスクを起動するときに値を読み、環境変数として渡す。

| 書き方 | タスク定義に残るもの | コンソールで見える |
|---|---|---|
| `environment`（ふつうの環境変数） | 値そのもの | 見える |
| **`secrets`** | シークレットの ARN だけ | ARN だけ |

パスワードを `environment` に書くと、タスク定義を見られる人なら誰でも読めてしまう。

このプロジェクトでは、DB の接続先を部品に分けて渡し、アプリの中で URL を組み立てる。

| 環境変数 | 渡し方 | 値 |
|---|---|---|
| `DB_HOST` | `environment` | RDS のエンドポイント |
| `DB_PASSWORD` | `secrets` | シークレット `statuspage/db-app` |
| `DB_PORT`・`DB_NAME`・`DB_USER` | アプリの既定値 | `5432`・`statuspage`・`statuspage` |
| `DATABASE_URL` | 渡さない | 渡したときはこちらを優先する（手元の Docker Compose） |

## 7. ログ

### EC2 のとき

アプリのログは、インスタンスの中（`journalctl`、`/var/log/cloud-init-output.log`）にあった。インスタンスが終了すると、ログも消える。

### ECS のとき

コンテナが標準出力（`print` やログの出力）に書いたものを、**ログドライバー** `awslogs` が **CloudWatch Logs** に送る。

| 言葉 | 意味 |
|---|---|
| ロググループ | ログの置き場所の単位。保存期間を決められる（このプロジェクトは1週間） |
| ログストリーム | ロググループの中の、1つのタスク（コンテナ）ごとの流れ。名前は `<プレフィックス>/<コンテナ名>/<タスクID>` |

タスクが止まっても、ログは CloudWatch Logs に残る。起動に失敗したタスクのログも、あとから読める。

### 止まったタスクの理由

ECS は、止まったタスクの **停止理由** を、しばらくの間（1時間ほど）コンソールに残す。

| 停止理由の例 | 意味 |
|---|---|
| `Essential container in task exited` | コンテナのプロセスが終了した（アプリのエラー） |
| `CannotPullContainerError` | イメージを取れなかった（タグがない、外に出る道がない、権限がない） |
| `ResourceInitializationError` | 起動の準備に失敗した（秘密を読めない、など） |
| `Task failed ELB health checks` | ALB のヘルスチェックに通らなかった |
| `Scaling activity initiated by (deployment ...)` | デプロイで入れ替えられた |

## 8. サービスのデプロイ

### ローリング更新

タスク定義が変わると（新しいイメージのタグなど）、サービスは古いタスクを新しいタスクに入れ替える。何個ずつ入れ替えるかは、2つの割合で決める。

| 設定 | 意味 |
|---|---|
| **minimumHealthyPercent** | 入れ替えの間、動かし続ける最低の割合（希望数に対して） |
| **maximumPercent** | 入れ替えの間、同時に動かしてよい最大の割合 |

| | 希望数 | 最低 | 最大 | 動き |
|---|---|---|---|---|
| api | 2 | 100% | 200% | 2個を動かしたまま、新しい2個を起動する。新しいものが ALB のヘルスチェックに通ったら、古いものを止める |
| worker | 1 | 0% | 100% | 古い1個を止めてから、新しい1個を起動する（監視の二重実行を避ける） |

Phase 6 の Auto Scaling グループのローリング更新（MinInstancesInService・MaxBatchSize）と同じ考え方を、台数ではなく割合で書く。

### 健康かどうかの判断

| 判断するもの | 内容 |
|---|---|
| コンテナが動いているか | プロセスが終了したら、そのタスクは失敗 |
| ALB のヘルスチェック（api） | `/healthz` が 200 を返すか。続けて失敗したら、ECS がタスクを止めて入れ替える |
| ヘルスチェックの猶予期間 | 起動してから、ALB のヘルスチェックの失敗を数えない時間。起動の遅いアプリが、準備中に止められないようにする |

Phase 6 の cfn-signal は、ユーザーデータが「成功した」と自分で言う仕組みだった。ECS では、ECS 自身がコンテナと ALB のヘルスチェックを見て判断する。

### デプロイのサーキットブレーカー

新しいタスクが起動に失敗し続けると、ECS は **デプロイが失敗した** と判断して止める（電気のブレーカーと同じく、失敗が続いたら回路を切る）。

| 設定 | 意味 |
|---|---|
| `enable: true` | 失敗が続いたら、デプロイを失敗にする |
| `rollback: true` | 失敗にしたら、最後に成功したデプロイ（前のタスク定義）に戻す |

- 何回失敗したら止めるかは、希望数から ECS が決める（少ないときは数回）
- CloudFormation は、サービスが安定する（新しいタスクがそろう）まで待つ。サーキットブレーカーが失敗にすると、CloudFormation の更新も失敗になり、スタック全体がロールバックする
- サーキットブレーカーがないと、ECS は新しいタスクを起動し続け、CloudFormation は長い時間（最大で数時間）待ち続ける

### ALB との受け渡し

| 場面 | 起きること |
|---|---|
| 新しいタスクが起動した | ターゲットグループに IP アドレスで登録される。ヘルスチェックに通ったら、リクエストが届き始める |
| 古いタスクを止める | 先にターゲットグループから外す。登録解除の遅延（Phase 4）の間、処理中のリクエストを終わらせてから止める |

### keep-alive のタイムアウト

ALB は、ターゲットとの接続を使い回す（keep-alive）。ALB は接続を60秒（アイドルタイムアウトの既定）まで使い回そうとする。アプリの側が先に接続を切ると、ALB がちょうどその接続でリクエストを送ったときに 502 エラーになる。

| | 接続を切るまでの時間 |
|---|---|
| ALB（アイドルタイムアウトの既定） | 60秒 |
| uvicorn の既定 | 5秒 |
| このプロジェクトのコンテナ | 65秒（`--timeout-keep-alive 65`）。ALB より長くする |

EC2 の構成では、間に nginx（既定 75秒）がいたので、この問題は起きなかった。

## 9. タスクの止まり方

ECS がタスクを止めるとき（入れ替え、手で止めた、など）は、次の順で進む。

| 順番 | 起きること |
|---|---|
| 1 | （api）ALB のターゲットから外す。登録解除の遅延の間、待つ |
| 2 | コンテナに **SIGTERM** を送る（「終わってください」） |
| 3 | **停止のタイムアウト**（既定30秒）まで、プロセスが自分で終わるのを待つ |
| 4 | まだ終わっていなければ **SIGKILL** を送る（強制終了） |

Phase 1 で、worker を「SIGTERM を受けたら今の回を終えてから正常終了する」ように作った。これは、まさにこの流れのため。監視の途中で強制終了されると、記録が中途半端になる。uvicorn も SIGTERM を受けると、処理中のリクエストを終えてから終わる。

| Dockerfile の書き方 | SIGTERM を受け取るもの |
|---|---|
| `CMD ["uvicorn", ...]`（exec 形式、このプロジェクト） | uvicorn 自身 |
| `CMD uvicorn ...`（シェル形式） | `/bin/sh`。アプリに届かず、タイムアウトまで待って強制終了されることがある |

## 10. パイプラインでイメージを作る

### Phase 6 からの変化

| | Phase 6 | Phase 7 |
|---|---|---|
| ステージ | ソース → テスト → デプロイ | ソース → テスト → **ビルド** → デプロイ |
| デプロイで渡すもの | コミット SHA（EC2 がコードを取ってくる） | コミット SHA（ECS がそのタグのイメージを取ってくる） |
| アプリを用意するのは | 各 EC2（起動のたび） | CodeBuild（1回だけ） |

### ビルドの段

1. ECR にログインする（`aws ecr get-login-password`）
2. そのコミット SHA のタグのイメージが、もう ECR にあるかを調べる。あれば作らない（同じコミットで「変更をリリース」し直したとき）
3. なければ `docker build` して、SHA のタグで ECR に push する

- CodeBuild で `docker` を使うには、プロジェクトの **特権モード**（privileged）を有効にする
- CodeBuild のマシンも ARM なので、`arm64` のイメージをエミュレーションなしで作れる
- **一度作ったイメージを、そのままデプロイする**（Build once, deploy many）。テストした中身と、動く中身が同じになる

### ビルドのロールの権限

| 許可 | 対象 |
|---|---|
| `ecr:GetAuthorizationToken` | すべて（ECR へのログインはリポジトリを指定できない） |
| イメージの push と確認（`ecr:PutImage`、`ecr:DescribeImages` など） | リポジトリ `statuspage` だけ |

### スタックの分け方

| スタック | 中身 | 寿命 |
|---|---|---|
| `StatuspageNetwork` | VPC、DB の SG | ずっと |
| `StatuspageDatabase` | RDS | ずっと（毎回止める） |
| **`StatuspageRegistry`**（新） | ECR のリポジトリ `statuspage` | ずっと。イメージを毎日消さない |
| `StatuspageApp` | ALB、ECS のクラスター・サービス・タスク定義、SG、ロググループ | 毎回作って消す |
| `StatuspagePipeline` | パイプライン、CodeBuild | ずっと |

パイプラインと App は、リポジトリを **名前**（`statuspage`）で参照する。スタックどうしの参照を作らないので、どれかを消しても他が困らない。

## 11. 費用

| もの | 料金 |
|---|---|
| Fargate | タスクの vCPU とメモリ × 動いた時間（秒単位、最低1分）。ARM は x86 より安い |
| パブリック IPv4 | タスク1個ごとに、EC2 と同じ料金 |
| ECR | 置いたイメージの量（GB × 月）。古いものはライフサイクルポリシーで消す |
| CloudWatch Logs | 送った量と置いた量。保存期間を決めておく |
| ALB・RDS | Phase 4〜6 と同じ |
| CodeBuild | ビルドの段が増える分、少し長くなる。デプロイは速くなる |

| 構成 | 計算のしかた |
|---|---|
| EC2（Phase 6） | `t4g.micro` × 3台 × 時間 |
| Fargate（Phase 7） | (0.25 vCPU の単価 + 0.5 GB の単価) × 3タスク × 時間 |

この大きさでは、どちらもほぼ同じ金額になる。Fargate は OS の管理がいらない分の上乗せがあるが、小さく切り出せるので無駄が出にくい。

## 12. ほかの Phase とのつながり

### Phase 6 から何が置き換わったか

| Phase 6 | Phase 7 |
|---|---|
| EC2 + Auto Scaling グループ | ECS のサービス（Fargate） |
| 起動テンプレート + ユーザーデータ | タスク定義 + イメージ |
| 起動のたびに GitHub と PyPI から取ってくる | CodeBuild が1回だけイメージを作り、ECR に置く |
| cfn-signal で、ユーザーデータが成功・失敗を知らせる | ECS がコンテナと ALB のヘルスチェックを見る。サーキットブレーカーで戻す |
| nginx が `X-Served-By` を付ける | アプリが `X-Served-By` を付ける |
| ログはインスタンスの中。消えると一緒に消える | CloudWatch Logs に残る |
| インスタンスのロール1つ | タスク実行ロールとタスクロール |

### この構成の弱点と、解決する Phase

| 弱点 | 解決 | Phase |
|---|---|---|
| worker は60秒ごとに数秒働くだけなのに、ずっと動いて課金される | EventBridge で時刻になったら Lambda を呼び、`run_once()` を1回だけ動かす | 8 |
| api も、リクエストがなくても動き続ける | 静的なページは S3 + CloudFront、API は Lambda に | 8 |
| ログは残るが、異常に気づく仕組みがない | メトリクスとアラームで知らせる | 9 |

## 13. 理解度チェック

答えは自分で考えてから開く。

<details>
<summary>Q1. EC2 + ユーザーデータで動かすのと比べて、コンテナで動かすと何がよくなる？</summary>

アプリの準備（パッケージ・ライブラリ・コード）を、イメージを作るときに1回だけ行う。起動するときはイメージを取ってきて動かすだけなので、速い。起動のたびに外のサービス（GitHub、PyPI）に頼らない。同じイメージなら、どのタスクも、手元の Docker も、中身が同じになる。
</details>

<details>
<summary>Q2. タスク定義・タスク・サービスは、それぞれ何？ EC2 の構成でいうと何に当たる？</summary>

タスク定義は、イメージ・CPU・メモリ・環境変数などを書いた設計図（起動テンプレートに当たる）。タスクは、そこから起動した動いているコンテナ（インスタンスに当たる）。サービスは、決めた数のタスクを動かし続け、ロードバランサーへの登録や入れ替えをする（Auto Scaling グループに当たる）。
</details>

<details>
<summary>Q3. サービスにせず「タスクを実行」で起動したタスクを止めると、どうなる？ サービスなら？</summary>

単独のタスクは、止めたらそのまま。誰も起動し直さない。サービスは、決めた数に戻すために、新しいタスクを起動する。
</details>

<details>
<summary>Q4. ECR のタグにコミット SHA を使い、タグのイミュータビリティを有効にするのはなぜ？</summary>

コミット SHA なら、どのコードから作ったイメージかが1対1で分かり、Phase 6 の `appVersion` と同じ値でデプロイできる。イミュータビリティを有効にすると、同じタグで別の中身に上書きできないので、「この SHA のイメージ」の中身があとから変わらない。
</details>

<details>
<summary>Q5. タスク実行ロールとタスクロールの違いは？ このプロジェクトで、DB のパスワードを読むのはどちら？</summary>

タスク実行ロールは、ECS がタスクを起動するときに使う（イメージを取る、ログを書く、秘密を読んで環境変数に入れる）。タスクロールは、コンテナの中のアプリが AWS の API を呼ぶときに使う。パスワードは、ECS が起動時に `secrets` から読んで環境変数に入れるので、タスク実行ロールが読む。
</details>

<details>
<summary>Q6. パスワードを、タスク定義の environment ではなく secrets で渡すのはなぜ？</summary>

`environment` に書くと、値そのものがタスク定義に残り、タスク定義を見られる人なら誰でも読める。`secrets` なら、タスク定義にはシークレットの ARN だけが残り、値は起動のときに ECS が読んで渡す。
</details>

<details>
<summary>Q7. NAT ゲートウェイがないのに、パブリックサブネットのタスクが ECR からイメージを取れるのはなぜ？ パブリック IP を付け忘れるとどうなる？</summary>

パブリック IP を持つタスクは、インターネットゲートウェイを通って ECR などの入口に出られる。付け忘れると外に出る道がないので、イメージを取れずに `CannotPullContainerError` で起動に失敗する。パブリック IP があっても、セキュリティグループで ALB からの 8000 番だけを許可しているので、外から直接は入れない。
</details>

<details>
<summary>Q8. api を minimumHealthyPercent 100・maximumPercent 200、worker を 0・100 にするのはなぜ？</summary>

api は、入れ替えの間も2個を下回らずに答え続けたいので、先に新しいタスクを足してから古いものを止める（最大で4個）。worker は、2個同時に動くと監視が二重になるので、古い1個を止めてから新しい1個を起動する（一時的に0個になる）。
</details>

<details>
<summary>Q9. デプロイのサーキットブレーカーは何をする？ ないとどうなる？</summary>

新しいタスクの起動の失敗が続いたら、デプロイを失敗にして、最後に成功したタスク定義に戻す。CloudFormation の更新も失敗になり、スタックがロールバックする。ないと、ECS は失敗するタスクを起動し続け、CloudFormation は長い時間待ち続ける。
</details>

<details>
<summary>Q10. EC2 のときは消えてしまったログが、ECS では残るのはなぜ？</summary>

コンテナが標準出力に書いたログを、ログドライバー `awslogs` がタスクの外（CloudWatch Logs）に送っているから。タスクが止まっても、ロググループの保存期間の間は読める。
</details>

<details>
<summary>Q11. ECS がタスクを止めるとき、コンテナには何が届く？ worker が SIGTERM で「今の回を終えてから」終わるのはなぜ大事？</summary>

まず SIGTERM が届き、停止のタイムアウト（既定30秒）の間に終わらなければ SIGKILL で強制終了される。worker が今の回を終えてから自分で終われば、監視の記録が中途半端にならない。exec 形式の `CMD` にしておかないと、SIGTERM がアプリに届かない。
</details>

<details>
<summary>Q12. パイプラインにビルドの段を足したのはなぜ？ 同じコミットで「変更をリリース」し直したとき、ビルドの段はどうする？</summary>

イメージを1回だけ作って ECR に置き、デプロイではそのイメージを使うため（テストしたものと動くものが同じになる）。同じ SHA のタグのイメージがすでにあれば、作り直さない（イミュータビリティで上書きもできない）。
</details>
